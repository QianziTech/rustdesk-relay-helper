## 1. 目标与范围

用户下载完整仓库或版本包后，在根目录运行 `bash manage.sh`，直接进入中文控制台引导界面。脚本支持安装、查看状态、修复、更新、回滚和卸载；程序安装目录可以选择，配置与状态初版使用固定系统路径。

本版不新增 `/usr/local/bin` 下的固定安装管理命令。已有业务命令 `rustdesk-relay-helper` 继续承担状态、探测、relay 切换等业务操作。安装管理与业务策略分工不变，策略合同以 [方案与技术选型](方案与技术选型.md) 为准。

目标环境为 Linux 宿主机、Python 3.9+、Bash 和正在运行的 systemd。Python 只使用标准库。管理器必须与 hbbs 共享网络命名空间，控制地址保持 `127.0.0.1:21115`。不安装、重建或升级 hbbs/hbbr，不接入 Docker socket，不自动安装系统依赖，不开放公网 WebUI。

## 2. 控制台入口

### 2.1 使用方式

```bash
# 下载后进入仓库根目录；也可使用脚本的绝对路径。
bash manage.sh
```

脚本根据自身位置定位源文件，不依赖当前工作目录。主菜单始终包含以下项目，并根据安装情况提示可用操作：

```text
RustDesk Relay Helper 安装管理
安装情况：未安装 / 已安装 / 安装不完整 / 发现已有手动部署
当前版本：……
程序目录：……

1. 安装
2. 查看状态
3. 修复
4. 更新
5. 回滚上一版
6. 卸载
7. 恢复中断维护
0. 退出
```

每项操作结束后显示结果并返回菜单；输入错误重新提示，取消返回上一级。非交互终端直接说明需要交互终端并退出，不使用默认答案执行安装。第一版不将命令行子命令、无人值守安装或固定管理命令作为交付要求。

安装时将 `manage.sh` 及其必要辅助文件一起放入受管程序版本目录。用户可从原下载目录重新运行，也可通过安装完成时展示的实际路径运行，例如 `bash /自选目录/current/manage.sh`。更新菜单明确区分“正在运行的脚本版本”“已安装版本”和“待更新版本”。

### 2.2 权限与确认

普通用户可以进入菜单、查看不需要特权的状态。读取受限配置或执行安装、修复、更新、回滚、卸载前，检查 root/sudo 权限；权限不足时提示用 sudo/root 重新运行菜单，本版不自动提权。权限不足不得显示为配置缺失。

实际修改前展示目标目录、将处理的服务、数据保留规则和版本变化，由用户确认。卸载中清除数据是单独的明确选择，默认不选。菜单关闭或确认前中断不产生部署变更。

## 3. 目录与权限

### 3.1 目录布局

初次安装建议默认程序根目录 `/usr/local/lib/rustdesk-relay-helper`，允许用户输入其他绝对路径；不强制放到 `/opt/rustdesk-relay-helper`。下载目录与安装目录分离，复制运行所需文件后，删除下载目录不影响运行。

```text
<程序根目录>/
  releases/<版本标识>/     # 完整程序、HTML、manage.sh 及必要辅助文件
  current -> releases/…   # 当前版本，由安装器维护

/etc/rustdesk-relay-helper/
  config.ini
  install.json            # 安装记录

/var/lib/rustdesk-relay-helper/
  state.json
  state.json.lock
  webui.token
  backups/                # 操作前备份，按需创建
```

初版仅支持一套安装。安装记录、配置和状态的位置固定，程序根目录可选。迁移程序根目录作为以后独立操作预留，更新不能悄悄改变安装路径。

### 3.2 权限规则

第一版沿用现有 root 服务模式，不引入专用服务用户。

| 对象 | 所有者 | 权限要求 |
| --- | --- | --- |
| 程序根目录、版本目录 | root:root | 通常 `0755`，普通用户不可写 |
| 普通程序文件、HTML、模板 | root:root | `0644` |
| 可执行脚本与业务命令入口 | root:root | `0755` |
| 配置目录 | root:root | `0750` |
| `config.ini` 与其备份 | root:root | `0640` |
| `install.json` | root:root | `0600` |
| 状态目录 | root:root | `0750` |
| 状态、token、维护锁、备份文件 | root:root | `0600` |
| 备份子目录 | root:root | `0700` |
| systemd 单元和受管 drop-in | root:root | `0644` |

代码目录与其父目录不得允许非特权用户写入或替换。目标目录的所有权、组写权限、其他用户写权限以及可用时的 ACL 都需要检查；不能只检查最后一级目录。禁止安装到任意用户可写的路径，包括普通用户的下载目录和临时目录。选择新路径时也检查最近存在的祖先目录。

程序根目录不能是 `/`、系统配置/状态根目录，或与源目录、配置目录、状态目录重叠。含空格的路径需正确处理 shell、systemd 参数和转义；无法可靠支持的路径字符应在部署前明确拒绝。

安装器拒绝来源不明的目标符号链接和路径冲突，只维护自身创建的 `current` 链接。只为受管文件设置所有权和权限，不对用户已有目录递归执行 `chown` 或 `chmod`。不存在的目录逐级创建并检查；已存在但不满足要求的祖先目录提示用户另选位置。

现有 WebUI 对 token 所有者和 `0600` 权限有硬性检查，安装、修复和更新必须保持这一条件。两个服务统一使用适当的 UMask，避免锁文件等新文件产生过宽权限。

### 3.3 路径一致性

安装器根据实际程序目录和检查通过的 Python 绝对路径生成业务入口与 systemd 单元。CLI、WebUI、reconcile 共用固定配置、状态和锁路径，不依赖用户环境变量，也不继承未经核对的 Python 模块搜索路径。

保留现有三个单元名称：`rustdesk-relay-helper.service`、`rustdesk-relay-helper.timer`、`rustdesk-relay-helper-web.service`。配置中 `probe_interval_seconds` 与 timer 间隔在安装时保持一致；后续 WebUI 修改不会自动同步 timer，状态页检测差异并提示，修复时经确认调整受管设置。管理员自行添加的 drop-in 保留，冲突展示为需要人工处理。

## 4. 安装记录与部署识别

`install.json` 是数据文件，通过 JSON 解析，不允许 `source` 或 `eval`。建议包含：记录格式版本、程序根目录、当前与上一版标识、程序提交 SHA、内容清单及校验值、Python 路径、受管单元和入口、安装时间、最近维护结果。

本地 Git 源可记录提交 SHA，同时检查工作区是否有修改；本地源码包无法可靠得出 SHA 时，记录内容摘要及“本地来源”，不得伪称官方版本。版本标识仅允许受限字符，不直接把输入拼接成目录。

无安装记录但发现现有入口、单元或配置时，视为“已有手动部署”，不直接覆盖或卸载。提供接管引导：核对文件路径和服务配置、预览备份及变更、经用户确认后生成记录；无法确认来源或范围时退出并给出需要人工处理的项。

安装记录损坏时不猜测删除范围。受管文件实际被修改时展示差异；修复和更新要明确处理该差异，不静默覆盖管理员改动。

## 5. 各项操作

### 5.1 安装

1. 检查系统、Python、Bash、systemd 可运行性、工具及目录权限；缺依赖时列出缺项并退出，不自动改系统软件源或安装软件。
2. 识别既有安装；已安装时引导修复或更新，不按首次安装覆盖数据。
3. 选择程序目录，检查源文件完整性和版本身份，准备独立版本目录。
4. 引导配置节点 ID、地址、层级、启用和 RTT 排名开关；策略提供已有默认值，由现有 Python 校验逻辑检查生成的 INI。
5. 真实配置已存在时保留并校验；示例域名即使格式有效也标记为未配置，不能以它们启动自动执行。
6. 生成业务命令入口、三个 systemd 单元及安装记录，执行 daemon-reload。
7. 询问是否启用本机 WebUI；启动前检查配置与端口占用。WebUI 始终只监听 `127.0.0.1`。
8. 显示版本、各路径、服务状态、再次运行 manage.sh 的方式及现场验收事项。

用户暂不提供真实节点时，可完成文件部署并记录“配置未完成”，所有服务保持停止；下次安装引导可以继续完成配置。部分失败需要显示已完成和未完成项，不能仅凭目录存在判定安装成功。

安装不调用 `switch`、`auto` 或写 relay 的 reconcile，不启用自动 timer。先确认服务器版本、`rs` 只读输出和真实客户端中继会话；自动执行的首次启用继续遵循 [实施规划](实施规划.md) 和 README。安装脚本本版不新增自动接管 relay 的快捷操作。

### 5.2 查看状态

分别显示安装完整性与业务运行情况：

- 安装版本、来源、程序目录、Python 版本和文件校验结果。
- 配置是否存在、有效、有真实节点；受管目录及文件权限是否正确。
- WebUI 与 timer 的启用、运行和失败状态；oneshot service 正常空闲不能判为故障。
- timer 实际间隔与配置期望是否一致，WebUI 监听地址和端口。
- 可选的 hbbs `rs` 只读结果、手动/自动模式和已有健康数据。

不探测节点、不保存业务状态、不修改配置或 relay、不输出 token。hbbs 连接失败显示“实际状态未确认”，不显示为空列表。权限不足、未安装、配置无效和接口不可达分别说明。缺少状态文件时不能为了查看而创建业务状态；如调用现有 CLI 会产生锁文件，需要明确限定或提供独立只读检查。

### 5.3 修复

按安装记录恢复当前版本的缺失文件、受管入口、单元和权限，校验后 daemon-reload。优先使用可信的本地版本副本；副本也损坏且手头源码版本不同，不能用另一版本冒充修复，需要走更新。

保留真实配置、状态、手动意图、token 和管理员 drop-in。配置丢失或损坏时展示问题，允许用户选择从已有有效备份恢复或重新配置，不直接用示例覆盖。token 存在时仅修复确认可修复的权限，不自动轮换；内容异常时报告并单独处理。

修复默认保持原服务启用状态；重启确有必要时先展示受影响服务。不能将网络不可达或 hbbs 错误当成需要重建容器的故障。

### 5.4 更新

第一版菜单支持选择“本地新版目录或版本包”。用户重新下载后，可以运行新版 `manage.sh` 选择更新，也可在现有脚本中指定新来源；不对生产目录直接 `git pull`，不要求安装目录必须是 Git 仓库。

更新按以下顺序执行：

1. 识别目标版本，校验文件完整性、Python 要求、安装记录格式，以及当前配置和状态的兼容性。
2. 将新版本准备在独立版本目录，准备单元和入口，确认前不改变当前程序。
3. 获取维护锁，记录原服务启用/运行状态；停止 timer，停止 WebUI，等待正在执行的 oneshot 完成。
4. 在与业务命令相同的状态锁下备份配置、状态、token、安装记录及受管部署文件，阻止维护期间的并发操作。
5. 切换当前版本、发布部署文件、daemon-reload，完成导入、配置校验及单元检查，再恢复原服务启用/运行状态。
6. 检查服务启动结果并保存完成记录，保留上一版；更新前关闭的 timer 仍保持关闭。

维护锁序列化两个 manage.sh；共享状态锁排斥 CLI/WebUI 的业务操作。锁与停服顺序必须统一，不能在等待服务退出时阻塞该服务取锁。锁超时报告“管理器忙”，不得删除锁文件强行解锁。

更新不主动执行业务切换；恢复原本开启的 timer 后会继续其既有自动策略，确认界面应说明。WebUI 重启使内存登录会话失效，但原 token 保留。

第一版禁止隐式、不兼容的数据迁移。发现配置或状态格式不兼容时在切换前终止；未来需要迁移时，另行定义版本范围、备份、转换及恢复协议。

更新失败时，恢复旧程序、单元、入口和记录，并在确认兼容后恢复旧服务。更新中断通过维护记录识别，下次运行提供恢复引导，不把半完成状态当作正常安装。

### 5.5 回滚

回滚到记录中的上一版，而非任意未知目录。先检查旧版能否读取当前配置和状态，再按更新的停服、锁及备份流程执行。默认保留当前业务数据，不自动恢复旧状态而丢失后续手动操作；确需从操作前备份恢复时，单独展示变化并要求确认。

程序回滚不撤销已经写入 hbbs 的 relay。若无法确认数据兼容性，阻止启动旧服务并说明原因。旧版本清理只处理受管目录，至少保留当前和上一版；第一版暂时保留全部受管本地版本。

### 5.6 卸载

确认后停止并禁用 timer、WebUI，等待正在执行的任务完成；使用维护锁和共享状态锁，防止并发维护。删除清单中的受管业务入口、单元和程序版本，daemon-reload；不修改 hbbs 当前 relay，不操作 hbbs/hbbr 容器。

默认保留配置、状态、token、备份及数据保留记录，显示保留路径。再次安装可识别这些数据。彻底清除是第二次明确选择，并逐项列出将删除的数据；不递归删除含无关文件的目录，不删除用户下载目录，也不依据未经校验的安装记录路径删除文件。

卸载程序包括受管副本的 manage.sh，因此删除自身所在目录应作为最后步骤处理。保留的原下载副本仍可用于重新安装。

## 6. 实现边界与失败处理

`manage.sh` 负责菜单、输入、权限引导和步骤分发。复用 Python 配置校验及文件锁；必要的安装记录、模板生成、校验和维护操作通过小型 Python 标准库辅助模块实现，Bash 不复制 relay 选择策略。

所有输入按数据传递，禁止 `eval`；外部命令使用明确参数，路径正确引用。只复制清单内的运行文件，不复制 `.git`、真实本地配置、状态、缓存或日志。版本包解压前检查路径穿越、绝对路径和危险链接，禁止将未知压缩包直接以 root 解到安装目录。

修改受管文件前备份，文件发布采用同文件系统临时文件及原子替换。部署整体不是天然原子操作，因此维护记录必须区分准备、切换、检查和完成阶段，并支持中断恢复。错误信息显示失败步骤、已完成变更与恢复方法，不泄露 token；取消或信号中断不能启动未完成部署的服务。

## 7. 后续 GitHub 在线入口

在线安装可以后续接入，但保持同一套本地安装逻辑：

```text
下载引导脚本 → 选择固定版本 → 下载完整版本包 → 校验 → 进入 manage.sh 引导界面
```

在线纯脚本只作为下载入口，本项目包含 Python 和 HTML，必须获取完整版本文件。引导脚本先下载到本地再执行，交互输入来自终端，避免管道占用标准输入。HTTPS 保持证书验证。

截至本设计基线，仓库尚无 GitHub Release。建议先交付本地脚本，再建立版本标签、Release 包及校验文件；默认选择稳定发布版，开发分支必须显式选择，选定后解析为固定提交，避免脚本与源码版本不一致。

校验摘要用于检测包损坏；与包同源的摘要不等同于独立来源认证。未来需要更强发布验证时再引入签名。网络失败必须发生在当前安装被改动之前，提供下载后本地安装的替代入口，不增加绕过 TLS 的选项。

在线更新复用本地更新流程，新增下载和版本选择环节；不另建一套安装器。本地第一版不强依赖联网、Git 或 GitHub API。

## 8. 验收与实施顺序

建议先实现菜单、安装记录、目录权限及本地安装；再实现状态、修复和卸载；最后实现本地更新、回滚和中断恢复。在线下载入口作为后续阶段。

验收应在可运行 systemd 的隔离 Linux 环境进行，至少覆盖：

- 从不同工作目录启动；普通用户/root；无交互终端；取消与错误输入。
- 默认及自定义路径，包括空格、不可写目录、不安全父目录和符号链接冲突。
- 首次安装、重复安装、配置未完成、已有手动部署接管、数据保留后重新安装。
